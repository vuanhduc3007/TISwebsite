# Media transaction safety

This change addresses the two data-loss paths in audit F02 without running a
migration or changing production data/provider assets. It does not turn MySQL and
Cloudinary into a distributed atomic transaction.

## Save and delete guarantees

- Product updates read the current slug/image reference using `SELECT ... FOR
  UPDATE` inside the transaction. A metadata-only request cannot restore an image
  reference taken before a concurrent replacement.
- Project updates and hard deletes lock the project row first, then read/lock its
  current image rows. Removed image IDs in a stale form produce an error; images
  added by another save and omitted from that form remain present. Appended image
  order starts after the current remaining rows. Image updates/deletes and parent
  deletes verify their affected-row count.
- Media keys are generated by the server for each upload and never accepted from
  form input. The actions do not attach an existing detached key to another row.
- When a query fails before COMMIT, new uploads are eligible for compensation only
  after an acknowledged ROLLBACK. A failure before any connection is acquired is
  also safe to compensate. Batch upload failure cleans only that batch's completed
  uploads before a database transaction starts.
- Once COMMIT has been attempted, a lost acknowledgement is an **unknown outcome**.
  The application never interprets a later ROLLBACK response as proof of failure.
  It preserves the new and old assets, destroys the uncertain pooled connection,
  and returns `SAVE_OUTCOME_UNKNOWN` for create/update with instructions to inspect
  the saved state before submitting again. A failed ROLLBACK similarly preserves
  assets and destroys the connection. No automatic transaction/upload retry occurs.
- After an acknowledged COMMIT, detached assets are checked against **both** the
  `products` and `project_images` tables before remote deletion. Shared legacy keys
  and soft-deleted product references remain protected. A failed reference query
  skips deletion. Provider delete failures do not change the saved result to an
  error; they leave orphan candidates for reconciliation.

The reference check depends on the application invariant that no mutation accepts
an old caller-supplied storage key. Future import/relink/restore features must not
violate this invariant. Out-of-band database writers must quiesce CMS writes and
media cleanup while importing/restoring references.

## Remaining limitations and operator workflow

MySQL and the media provider do not share a commit protocol. A process crash,
provider timeout, or ambiguous transaction can leave extra assets. There is no
durable cleanup outbox or cross-request operation/idempotency ledger in this
change. Re-submitting a create/update after response loss can create an additional
project or upload; the client must inspect saved state before retrying. Product
slug uniqueness is not a general idempotency guarantee.

An unknown save should be resolved by an authorized operator using a fresh DB
connection and provider inventory. Preserve media while the outcome remains
uncertain. Do not delete based only on a failed request, a rollback acknowledgement
after COMMIT, or a time threshold. If the transaction committed, keep all assets
referenced by the committed rows. If it did not, its unattached uploads can be
reviewed as orphan candidates.

For the existing reconciliation script, a dry run is an inventory snapshot, not
authorization to delete. Before an approved production delete pass:

1. Pause CMS media mutations and out-of-band imports/restores; wait for in-flight
   uploads and DB transactions to finish and resolve uncertain saves.
2. Check current product/project references, the exact provider account/namespace,
   and a fresh dry-run candidate list. Preserve the required baseline
   **4 categories / 157 products / 8 projects / 18 project images** and recorded IDs.
3. Obtain the existing explicit production-cleanup approval and run only the
   reviewed operation. Keep records of the result and any remaining orphans.
4. Resume writes after verifying every surviving DB media reference resolves.

The age threshold alone cannot prove a Cloudinary asset is unreferenced: a long
running upload/transaction can still be in flight. Nothing in this remediation
authorizes production reconciliation, deletion, DB reads, or uploads.

## Verification and acceptance still required

`tests/media-transaction-safety.test.mjs` transpiles the actual source actions and
helper, with an import allowlist and mocked DB/auth/provider/Next modules. It
checks COMMIT acknowledgement loss, ROLLBACK loss, lock deadlock/timeout, partial
batch upload failure, concurrent replacements and metadata saves, stale project
image membership, zero-effect deletion, shared references, and cleanup failures.
It does not read an env file, open a DB connection, or send a provider request.

Run with the application's normal `npm test`, or:

```text
node --conditions=react-server --experimental-strip-types --test tests/media-transaction-safety.test.mjs
```

These are source-action tests with a modeled row lock, **not** real MySQL locking,
Cloudinary, or end-to-end HTTP verification. Before closing F02 fully, run an
approved disposable integration environment with independent test DB/provider
credentials: two simultaneous saves, edit versus hard delete, connection loss
before/after COMMIT, process termination, provider failures, and reconciliation.
Assert each surviving reference resolves, and that all residual assets are
accounted for. Decide whether retry idempotency and a durable cleanup outbox are
required before accepting the remaining operational risk. Do not use production
credentials or the production database for these tests.
